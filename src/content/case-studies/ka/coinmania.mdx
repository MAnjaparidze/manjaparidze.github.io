## რა არის Coinmania?

Coinmania კრიპტო საფულე და გადახდების აპლიკაციაა საქართველოსთვის. პლატფორმას ვებსა და მობილურზე 150–200
ათასი აქტიური მომხმარებელი ჰყავს და თვეში მრავალმილიონიანი ბრუნვა აქვს, აპლიკაციას კი App Store-ზე 5.0 და
Google Play-ზე 4.8 შეფასება აქვს. აპლიკაციაში შეგიძლიათ:

- ნახოთ თქვენი აქტივები და ფასები რეალურ დროში, იყიდოთ, გაყიდოთ ან გადაცვალოთ კრიპტო;
- შეიტანოთ და გაიტანოთ კრიპტო ბლოკჩეინზე, შენახული მისამართებითა და თითოეული აქტივისთვის ქსელის არჩევით;
- გადარიცხოთ თანხა ბანკიდან და ბანკში, შენახული ანგარიშებით;
- გადაიხადოთ კომუნალური გადასახადები კრიპტოთი, ნაბიჯ-ნაბიჯ ოსტატითა და შენახული შაბლონებით;
- გადაიხადოთ პარტნიორ მაღაზიებში QR კოდით ან ბმულით (მუშავდება);
- გაიაროთ ვერიფიკაცია აპლიკაციაშივე და მართოთ უსაფრთხოება, ორფაქტორიანი ავთენტიფიკაცია და შეტყობინებები.

აპლიკაცია ქართულ და ინგლისურ ენებზეა.

## როგორ არის აწყობილი აპლიკაცია?

ეს არის bare React Native 0.79, React 19-ითა და TypeScript-ით, ჩართული New Architecture-ითა და Hermes-ით.
ნავიგაცია React Navigation 7-ის native-stack-ია, სადაც ყველა მარშრუტის სახელი და პარამეტრი ტიპიზებულია.
სტეიტი სამ ადგილას ცხოვრობს და თითოეული იმის მიხედვითაა არჩეული, რას ინახავს:

| ფენა | რას ინახავს | რატომ |
| --- | --- | --- |
| React Query | სერვერის ყველა მონაცემს, მონაცემის ტიპის მიხედვით განსაზღვრული სიახლის ვადით: საათები აქტივების კატალოგისთვის, ნული გადახდის ცოცხალი მონაცემებისთვის | ქეშირება, ხელახალი მცდელობები და ინვალიდაცია თავისთავად |
| Zustand (7 სთორი) | კლიენტისა და პროცესების სტეიტს: აქტივების კატალოგს ID-ით, KYC სტატუსს, OTP ალმებს, სესიის დაბლოკვას, გადასახადების ოსტატს | სტეიტი, რომელიც სერვერის მონაცემი არ არის |
| Context | თემასა და WebSocket კავშირის სტატუსს | მნიშვნელობები, რომლებსაც მთელი აპლიკაცია კითხულობს |

API ფენა პატარა და მკაცრია. როცა რამდენიმე მოთხოვნა ერთდროულად აღმოაჩენს ვადაგასულ ტოკენს, ისინი ერთ
განახლებას იზიარებენ და მის უკან რიგში დგანან. აპლიკაცია საათს სერვერის `Date` ჰედერით ასწორებს, ამიტომ
უკუთვლები ტელეფონის დროზე არ არის დამოკიდებული. კომუნალური გადასახადებისა და QR გადახდების პასუხები UI-მდე
ტიპიზებულ პარსერებს გადის.

## როგორ აღწევს ფასები ეკრანამდე ისე, რომ ყველაფერი თავიდან არ დაიხატოს?

ბექენდი კლასიკურ ASP.NET SignalR-ს იყენებს, ამიტომ პროტოკოლი ხელით დავწერე ნატიურ WebSocket-ზე, SignalR-ის
კლიენტური ბიბლიოთეკის გარეშე. კლიენტი კავშირის ტოკენზე თანხმდება, ხსნის ფასების ჰაბს და 30 წამიანი
დაკავშირების ტაიმაუტის შემდეგ ჩერდება. აპლიკაციის ფონზე გადასვლისას კავშირს წყვეტს, დაბრუნებისას თავიდან
უკავშირდება და ცდის ექსპონენციური ინტერვალებით.

თითოეული მიღებული პაკეტი პირდაპირ React Query-ის ქეშში ერწყმის, აქტივის მიხედვით, ამიტომ ნაწილობრივი
განახლება აქტივს არასოდეს კარგავს და არც ერთ ეკრანს ხელახლა მოთხოვნა არ სჭირდება:

```ts
// Simplified from usePriceUpdates
queryClient.setQueryData<PriceMap>(['assets-prices'], (prices = {}) => {
  const next = { ...prices };
  for (const update of batch) next[update.assetId] = update;
  return next;
});
```

სიაში ფასის თითოეული რიგი მემოიზაციის საკუთარ შედარებას იყენებს, ამიტომ ყოველი ცვლილება თავიდან ხატავს
მხოლოდ იმ რიგებს, რომელთა ფასიც შეიცვალა. ბალანსები REST-ით მოდის, ნელი მონაცემები კი პერიოდულად მოწმდება:
სავაჭრო წყვილები ყოველ 10 წამში, ფონზე კი ჩერდება.

## როგორ არის სესია ერთ მოწყობილობაზე მიბმული?

Refresh ტოკენები მიბმულია გასაღებზე, რომელიც ტელეფონს არასოდეს ტოვებს. თითოეული მოწყობილობა საკუთარ
გასაღებს არეგისტრირებს, რომელიც დაცულ აპარატურაში ინახება და ბიომეტრიით იხსნება, ან მომხმარებლის PIN-ით
არის დაცული. რეგისტრაციას ერთჯერადი კოდი სჭირდება და სერვერზე მხოლოდ საჯარო გასაღები მიდის.

როცა სერვერს მტკიცებულება სჭირდება, ის გამოწვევას აგზავნის. აპლიკაცია იბლოკება და მომხმარებელი გამოწვევას
ბიომეტრიით ან PIN-ით აწერს ხელს. ყველა მოთხოვნა, რომელიც ამ გამოწვევას ელოდება, ერთ promise-ს იზიარებს 60
წამიანი ტაიმაუტით. ამან რეალური ბაგი გამოასწორა: მის გარეშე დაბლოკვის ეკრანი შეიძლებოდა გაჭედილიყო და
აღარასოდეს დახურულიყო.

თანხის გადარიცხვა მეტს მოითხოვს. გატანები და გადასახადები დამატებით დადასტურებას გადის, რომელიც მომხმარებელს
ყველა იმ ფაქტორზე ატარებს, რასაც სერვერი ითხოვს, მათ შორის SMS ან WhatsApp კოდებსა და Google
Authenticator-ზე. ვერიფიკაცია აპლიკაციაშივე მიმდინარეობს Identomat SDK-ით.

## რა გაფუჭდა და როგორ გამოსწორდა?

რთული პრობლემების უმეტესობა JavaScript-ის ქვემოთ იყო. ნატიური და ბიბლიოთეკების ხუთი გამოსწორება პაჩების
სახით ინახება:

- **Reanimated რელიზ ბილდებში.** რელიზ ბილდები worklet-ების გამოძახებებს დაცვის გარეშე უშვებდა, ამიტომ
  worklet-ის ნებისმიერი exception აპლიკაციას კლავდა. პაჩი რელიზ ბილდებსაც აიძულებს, დაიჭირონ და
  დაარეპორტონ ის, როგორც dev ბილდები აკეთებენ.
- **iOS-ის შეცდომა `@gorhom/bottom-sheet`-ში.** worklet-ი `{ window }`-ს ადესტრუქტურებდა, გლობალურ ცვლადს
  ფარავდა და აგდებდა „Property 'window' doesn't exist“. გამოსწორებამ ის გადაარქვა და გაჟონილი `Dimensions`
  listener-ები წაშალა.
- **ბიომეტრია iOS-ზე.** ფონურ რიგზე შესრულებული promise-ები ახლა მთავარ ნაკადზე სრულდება, როგორც
  ბიბლიოთეკის სხვა მეთოდები.
- **React Native codegen-ის ორი გამოსწორება:** nil-ისგან დაცული კომპონენტების რუკა და მასივის ტიპის
  სწორი განსაზღვრა.

კიდევ ორი გამოსწორება ისეთივე მნიშვნელოვანი იყო, როგორც ნებისმიერი პაჩი:

- **TypeScript-მა ჩუმად შეწყვიტა შემოწმება.** მოძველების ალამმა ტიპების შემოწმება გათიშა. მისი დაბრუნება
  ცხად გზებს, TypeScript 5.9-ს და ყველა იმ შეცდომის გასწორებას მოითხოვდა, რომელსაც ის მალავდა.
- **ენის შეცვლისას ძველი ტექსტი ჩანდა.** მოთხოვნების გასაღებები ენას არ შეიცავდა, ამიტომ ქეში ახლა ენის
  შეცვლისას იწმინდება.

კომუნალური გადასახადების ოსტატი ერთი ეკრანია, რომელსაც სთორი მართავს, და არა ათეულამდე stack მარშრუტი; მისი
ოთხი ნაბიჯი კი საერთოა შენახული შაბლონებისა და გადახდებისთვის.

## როგორ ვმუშაობ სამკაციან გუნდში?

Coinmania-ს აპლიკაციაზე სამი ინჟინერი მუშაობს. აპლიკაციის არქიტექტურის ინიციატორი ვიყავი, იმ საწყის
სტრუქტურაზე რჩევებს ვაძლევდი, საიდანაც გუნდმა დაიწყო, და პირველივე კვირიდან ვწერ კოდს. დღეს:

- ჩემზე მოდის **კომიტების 57%** და **მიმდინარე კოდის 46%**.
- ვარ **რელიზებზე** პასუხისმგებელი: დღემდე ყველა 1.x რელიზი, fastlane-ის ლაინებით iOS-ისა და Android-ისთვის.
- ვხელმძღვანელობ **API ფენას, ნავიგაციასა და ნატიურ iOS და Android სამუშაოს**.
- სამუშაო **pull request-ებით** მიდის (დღემდე 281), Jira-ს გასაღებიანი ბრენჩებით.
- დავამატე **pre-push დაცვა**, რომელიც push-ს ბლოკავს, თუ ტიპების შემოწმება ან unit ტესტები ვარდება, და
  დავწერე აპლიკაციის **97 ტესტი**, რომლებიც ფარავს გადასახადების ლოგიკას, API კონტრაქტებს, პარსერებს,
  შეცდომების მეპინგსა და QR გადახდებს.

## რას გავაკეთებდი სხვანაირად?

- **ტესტებსა და CI-ს პირველივე დღიდან დავამატებდი.** პირველი რეალური ტესტები დაახლოებით 18 თვის შემდეგ
  გაჩნდა, ლოკალური hook-ები კი დღემდე ერთადერთი დაცვაა.
- **ნატიურ პაჩებს იმ კოდთან ერთად დავაკომიტებდი, რომელსაც ისინი სჭირდება.** ერთი გამოსწორება დაუკომიტებელი
  დარჩა და შეცდომა ყოველ სუფთა checkout-ზე ბრუნდებოდა, სანამ არ დაკომიტდა.
- **რელიზებს თეგებს დავადებდი.** ვერსიების აღდგენა ახლა ბილდის ფაილებიდან უწევთ.
- **lockfile-ებს სტაბილურად შევინარჩუნებდი.** დამოკიდებულებების ცვლილებები ისტორიის ყველაზე დიდ კომიტებს
  შეადგენს.
- **პროდუქტის გადაწყვეტილებებს აწყობამდე დავაზუსტებდი.** მკაცრი KYC ოთხჯერ ჩაირთო და გაითიშა.
