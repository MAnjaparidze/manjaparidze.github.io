## რა არის UKar?

UKar ავტორეცხვის მყისიერი დაჯავშნის პლატფორმაა აზერბაიჯანელი მძღოლებისთვის, შემდეგ კი საქართველოსთვის.
მძღოლი UKar-ის აპლიკაციაში რეცხვას ითხოვს, პლატფორმა კი შეკვეთას უახლოეს თავისუფალ სამრეცხაოს სთავაზობს.
მიღებულ რეცხვას მძღოლი რუკაზე რეალურ დროში ადევნებს თვალს, მისვლიდან დასრულებამდე, ბოლოს კი აფასებს
ვარსკვლავებით, თეგებითა და კომენტარით.

სამრეცხაოები ყველაფერს მეორე აპლიკაციიდან, UKar Partner-იდან მართავენ. მფლობელები მართავენ ფილიალებს,
სერვისებს, ფასებსა და თანამშრომლებს; ადმინისტრატორები და მრეცხავები ხელმისაწვდომ სტატუსზე გადადიან, იღებენ
მოთხოვნებს და თითოეულ რეცხვას ეტაპებზე ატარებენ. ვებ ადმინ პანელიდან UKar-ის გუნდი ამტკიცებს ახალ
პარტნიორებს, ამოწმებს სამრეცხაოების ცვლილებებს და თვალს ადევნებს ყველა რეცხვასა და შეფასებას. აპლიკაციები
ოთხ ენაზეა: ინგლისურად, რუსულად, აზერბაიჯანულად და ქართულად.

## რა სჭირდება ერთ დეველოპერს ორმხრივი მარკეტპლეისის ასაწყობად?

ერთი ბექენდი და სამი კლიენტი. ერთიანი Node.js, Express და MongoDB ბექენდი Socket.IO-ით რეალურ დროში
უგზავნის განახლებებს მომხმარებლისა და პარტნიორის აპლიკაციებს, ორივე React Native-სა და Expo-ზე iOS-ისა და
Android-ისთვის, ასევე React და TypeScript ადმინ პანელს. ამ ბირთვის გარშემოა Yandex MapKit და Geocoder, Expo
push შეტყობინებები, SMS ერთჯერადი კოდით შესვლა და DigitalOcean Spaces სურათებისთვის.

## როგორ ხდება მობილურზე რეალურ დროში სტატუსი საიმედო?

სერვერი უნდა იყოს სიმართლის ერთადერთი წყარო, თითოეულ აპლიკაციას კი ერთი აღდგენის რუტინა უნდა ჰქონდეს.
Socket.IO-ის ოთახები, თითო მომხმარებელზე და თითო სამრეცხაოზე, რეალურ დროში გადასცემს განახლებებს, მაგალითად,
პარტნიორისკენ მიმავალი მომხმარებლის ლოკაციას. მაგრამ მხოლოდ სოკეტის მოვლენები ტელეფონებზე საიმედო არ არის:
აპლიკაციებს ხურავენ, ფონზე გადადის, კავშირი წყდება, და გამოტოვებული მოვლენა დაკარგულ რეცხვას ან ეკრანზე
გაჭედილ შეთავაზებას ნიშნავდა.

ამიტომ თითოეული აპლიკაცია ახლა ერთსა და იმავე აღდგენის რუტინას უშვებს ცივი გაშვებისას, push შეტყობინებაზე
დაჭერისას, წინა პლანზე დაბრუნებისას და სოკეტის ხელახლა მიერთებისას: ეკითხება სერვერს, რა ხდება სინამდვილეში,
და ეკრანს ამის მიხედვით თავიდან აწყობს. როცა აპლიკაცია ფონზეა, Expo push შეტყობინებები ფარავს შეთავაზებებს,
სტატუსის ცვლილებებსა და შეფასებების გადაწყვეტილებებს.

სესიები იმავე პრინციპით მუშაობს. შესვლა ერთ მოწყობილობაზეა შეზღუდული ისე, რომ მოწყობილობის შეცვლა ყოველ
ჯერზე ახალ SMS კოდს არ ხარჯავს, refresh ტოკენების როტაცია კი უძლებს აპლიკაციის დახურვას განახლების შუაში.

## როგორ ჩავრთოთ Yandex Maps React Native 0.83-სა და Expo SDK 55-ში?

iOS-ისთვის Expo config plugin-ით, Android-ისთვის კი შენარჩუნებული ფორკის პაჩით. ორივე მობილური აპლიკაცია
ნატიურ MapKit-ს იყენებს; ადმინ პანელი სამრეცხაოების რუკაზე მოსანიშნად `@pbe/react-yandex-maps`-ს იყენებს.

Yandex პარტნიორების მოთხოვნა იყო, და მიზეზით: ბაქოსა და თბილისის რუკების ადგილობრივი დეტალები მასთან
სხვა ალტერნატივებზე უფრო მკაფიო და განახლებულია.

### iOS: MapKit-ის ინიციალიზაცია React Native-ის გაშვებამდე

MapKit SDK-ის ინიციალიზაცია Swift AppDelegate-ში React Native bridge-ის გაშვებამდე უნდა მოხდეს, თორემ რუკის
პირველი ხედი ჯერ არაინიციალიზებულ SDK-ზე იტვირთება. ნატიური ფაილების ხელით რედაქტირების ნაცვლად, config
plugin (`withYandexMaps`, Expo-ს `withAppDelegate`-ით) AppDelegate-ს prebuild-ის დროს თავად ცვლის. ის ამატებს
იმპორტს და React Native factory-ის შექმნისთანავე ორ გამოძახებას სვამს:

```swift
import YandexMapsMobile

// Injected by withYandexMaps after the React Native factory is created.
// The key comes from extra.mapKitApiKey, never hard-coded.
YMKMapKit.setApiKey(mapKitApiKey)
YMKMapKit.sharedInstance()
```

ერთი ხაფანგი: გასაღები prebuild-ის დროს იწერება. მისი შეცვლა iOS-ზე მომდევნო prebuild-მდე არ ვრცელდება,
Android კი მას JavaScript-იდან გაშვების დროს კითხულობს. iOS-ზე მომუშავე რუკა სულაც არ ამტკიცებს, რომ ახალი
გასაღები ბილდში მოხვდა.

### Android: Kotlin 2.1-ის nullability

React Native 0.83 Kotlin 2.1-ს მოითხოვს, `react-native-yamap@4.8.3` კი მასზე აღარ კომპილირდებოდა. Kotlin
2.1-ის უფრო მკაცრი შემოწმებები უარყოფდა გამოძახებებს შესაძლო null მნიშვნელობებზე. პირველი გამოსავალი
`patch-package`-ის პაჩი იყო: უსაფრთხო გამოძახებები (`?.`), `?: continue` და `?: return` დაცვები, ასევე
`Arguments.fromList(value ?: emptyList())` null-ის შემცველი ტრანსპორტის სიებისთვის.

შემდეგ მომხმარებლის აპლიკაცია გადავიდა შენარჩუნებულ ფორკზე, `react-native-yamap-plus`-ზე, რომელიც ახალ
ინსტრუმენტებს უჭერს მხარს. მას ისევ ახლავს პაჩი ორი ორიგინალური ბაგისთვის:

- მარშრუტის შედეგი მხოლოდ ლოკალიზებულ ხანგრძლივობას აბრუნებდა, მაგალითად „12 мин“. პაჩი ამატებს
  ხანგრძლივობას წამებში, რაც ETA-ს გამოთვლას სჭირდება.
- iOS-ის ერთ-ერთი ჰენდლერი გასაღებსა და მნიშვნელობას არეული რიგით აგზავნიდა.

### რა არ გამოვიდა პირველად

- **Gradle-ის ინკრემენტულმა ბილდებმა Kotlin-ის შეცდომები დამალა** უკვე დაკომპილირებულ ფაილებში, ამიტომ
  გამოსწორებები დასრულებულად ჩანდა, სანამ სრულმა სუფთა ბილდმა არ ჩაიშალა.
- **პაჩის ხელახლა გენერირებამ**, როცა ბიბლიოთეკის Android `build/` საქაღალდე ჯერ კიდევ არსებობდა, ბილდის
  ფაილებიც შიგ გადაიტანა: ერთხელ 2-ფაილიანი პაჩი 373 ფაილის ცვლილებად იქცა.

მიგრაციასა და ნატიურ ხელახლა აწყობას კალენდარული დროით დაახლოებით ერთი კვირა დასჭირდა, კომიტების თარიღების
მიხედვით.

### რაზე ვთქვი უარი

- **რუკის ბიბლიოთეკის საკუთარი ფორკის შენახვაზე.** პაჩები ამის ნაცვლად `patch-package`-შია. ფასი
  დოკუმენტირებული ხაფანგია: პაჩის ფაილი ზუსტ ვერსიას ემთხვევა, ამიტომ ვერსიის აწევისას პაჩი ჩუმად
  გამოიტოვება და ETA უშეცდომოდ ფუჭდება.
- **პარტნიორის აპლიკაციის იმავე ნაბიჯით განახლებაზე.** ის განზრახ რჩება Expo SDK 52-სა და Kotlin 1.9-ზე,
  ორიგინალური ბიბლიოთეკითა და საკუთარი პაჩით, რომ ერთმა მიგრაციამ მეორე არ შეაფერხოს. ფასი: რუკის
  გამოსწორება ერთ აპლიკაციაში მეორეზე არ გადადის.

## როგორ ვაწყობ ოთხ კოდბაზას მარტო?

ვმუშაობ Claude Code-თან, Anthropic-ის AI ასისტენტთან პროგრამირებისთვის, როგორც საინჟინრო პარტნიორთან. მე
ვადგენ მიმართულებას, ვწყვეტ, როგორ უნდა მოიქცეს პროდუქტი, და თითოეულ ცვლილებას ვამოწმებ და ვტესტავ. Claude
მეხმარება საუკეთესო პრაქტიკების კვლევაში, რამდენიმე აპლიკაციაზე გადაჭიმული ცვლილებების დაგეგმვაში, კოდის
